# A314 clockport interface (branch A314_NETWORK)

Work in progress: the Amiga talks to the FPGA Companion through the A314 protocol (Niklas Ekström,
`a314.device` + `a314eth.device`, CC0 clockport variant). The Companion plays the Raspberry Pi.
Evaluation and comparison with PLIP / X-Surf: project "PLIP_PPP_NETWORK", `a314-evaluation.md`.

## What is here

| file | what |
|---|---|
| `src/minimig-aga/a314_cp.v` | register block of the CPLD `cp_pi_if.v` (4 byte registers, 16 bit pointer with auto-increment, interrupt bits), dual-port RAM (`AW` = 13, 8 KB = 4 BSRAM) |
| `src/misc/a314_host.v` | SPI target 6: the Companion reads/writes the RAM and sets/clears the interrupt bits |
| `src/misc/mcu_spi.v` | `ifdef ENABLE_A314`: target 6, `mcu_a314_strobe` / `mcu_a314_din` |
| `sim/a314/` | `run.sh`, `tb_a314_cp.v` (66 checks), `tb_spi_a314.v` (23 checks, real `mcu_spi.v` at bit level), `tb_bus_a314.v` (98 checks, real `gary.v` + bridge) |

Companion side: branch `A314_NETWORK` of FPGA-Companion (`src/a314_proto.c`, `src/rp2040/a314_port.c`, `test/a314/`).

## Registers (Amiga, byte access at `ClockportAddress + reg * 4`, default `$D80001`)

| reg | name | |
|---|---|---|
| 0 | SRAM | read/write `RAM[ptr]`, then `ptr + 1` (read and write) |
| 1 | IRQ | read: bit 0 = cp_irq. write: bit 7 = 1 sets, bit 7 = 0 clears the bits [1:0] that are 1. bit 0 = INT6 to the Amiga, bit 1 = interrupt of the Pi |
| 2 | A_LO | `ptr[7:0]` (write) |
| 3 | A_HI | `ptr[15:8]` (write) |

Same semantics as `cp_pi_if.v` of the original (checked against its source). The driver assumes 64 KB
(`MEM_SIZE` in `memory_allocator.c`), the RAM here is 8 KB: `a314eth.device` allocates 4 x 1520 bytes from
address 520 and stays below 8 KB, a second A314 application that allocates more would alias. The Companion
refuses frames outside of the RAM. `AW = 14` (16 KB, 8 BSRAM) is a parameter away.

## SPI target 6 (`a314_host.v`)

Byte 0 = target 6, byte 1 = command. The reply to a byte is the answer to the byte before it (like `plip_host.v`),
reply 1 of every command is the status `{7'b0, pi_irq}`.

| cmd | bytes | reply |
|---|---|---|
| 0 STATUS | - | status |
| 1 READ | addr hi, addr lo, 0, then N x 0 | the N bytes after the 0 are `RAM[addr ..]` |
| 2 WRITE | addr hi, addr lo, data ... | - |
| 3 IRQ | value | - (written like the Pi writes REG_IRQ: `0x02` clears pi_irq, `0x81` raises INT6) |
| 4 ID | 0, 0, 0 | status, `0xA3`, version 1, AW |

`irq` of `a314_host` = `pi_irq` (level) for `int_in[6]` of `sysctrl.v`.
Bytes need a gap (100 ns .. 2 us tested), a block transfer without gap is too fast for `mcu_spi.v` (as for PLIP).

## Integration in the core (`ifdef ENABLE_A314`)

| file | what |
|---|---|
| `gary.v` | `sel_a314` = `$D80000 - $D8FFFF`, taken out of `sel_reg` (otherwise the cycle would hit the custom chip registers) |
| `minimig_m68k_bridge.v` | new output `cyc` (a CPU bus cycle is going on, read or write) |
| `minimig.v` | glue + `a314_cp`, INT6 = `int6 \| int6_toccata \| int6_a314`, read data into the CPU data multiplexer (both bytes, like the RTC) |
| `nanomig.v` | `a314_host` (reset = `por`, survives an Amiga reset), ports `a314_strobe/start/din/dout/irq` |
| `tang/nano20k/top.sv`, `top_020.sv` | SPI target 6 of `mcu_spi`, `int_in[6]`, `// \`define ENABLE_A314` (off by default) |
| `scripts/build.tcl`, `build_020.tcl` | the two new files |

One bus cycle is one access: at the start of the cycle (`cyc` rises) the glue decides whether it belongs to the
A314 and which register is meant, the first write strobe takes the data, the side effects happen once when the
cycle ends. `sel_a314`/`cpu_rd`/`cpu_lwr` alone are not enough: with the TG68K the address of the next access is
on the bus for one clock while the old cycle is still seen as active (found by `tb_bus_a314.v`).

`sim/a314/tb_bus_a314.v` runs the real `gary.v`, `minimig_m68k_bridge.v`, `amiga_clk.v` with the glue taken
verbatim from `minimig.v` (98 checks): 68000 cycles (fast and slow) and the chip bus cycles of the TG68K state
machine of `cpu_wrapper.v`, back to back, with other addresses in between and with Agnus taking the bus.
`minimig.v` elaborates with iverilog with and without `ENABLE_A314` / `ENABLE_PLIP` / `ENABLE_RTC`.

## To build and test

1. In `top.sv` or `top_020.sv` enable `` `define ENABLE_A314 ``. It needs 4 BSRAM blocks more; if the 020 build
   does not fit, switch `ENABLE_PLIP` off (2 blocks) or free blocks elsewhere. Not tried: no Gowin run was done.
2. Companion: firmware of the branch `A314_NETWORK`, `config.ini`: `[A314]` `ENABLE=1`, `PEER=<address of the Amiga in the lan>`.
3. Amiga: `a314-cp.device` as `DEVS:a314.device`, `DEVS:a314.config` with `ClockportAddress = D80001` and
   `Interrupt = 6`, `a314eth.device` in `DEVS:Networks`, Roadshow interface with `device=a314eth.device`.

Not covered by the simulations: `nanomig.v` and the top level (port plumbing only, cannot be elaborated without the
Gowin primitives), timing/fit, the real drivers. `top_lcd.sv` is not wired (it has no PLIP wiring either).
